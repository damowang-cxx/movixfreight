# 总体架构与供应商接入

## 1. 总体架构方向

### 已确认

- 管理员端和客户端是两个独立网站；
- 两个网站访问同一个后端系统；
- 后端根据身份、角色和客户归属控制权限与数据范围。

### 建议方案

初期采用模块化单体，而不是直接拆分微服务。内部按领域划分模块，并使供应商接口与核心订单、资金业务解耦。

建议后端接口边界：

```text
/api/admin/v1/*       管理员网站接口
/api/customer/v1/*    客户网站接口
/api/open/v1/*        客户 ERP 和第三方系统接口
```

## 2. 供应商接入类型

**已确认**需要支持：

1. 官方接口，例如 UPS、FedEx、DHL 官方 API；
2. 第三方供应商或代理商自有接口；
3. 通过中转站调用官方或近似官方协议的接口。

## 3. 可插拔设计原则

### 建议方案

对接能力分为两层：

- **驱动层**：只有出现新的接口协议时才开发新代码；
- **实例层**：在数据库中配置供应商、账号、地址、密钥、产品和环境。

因此，“新增供应商”不一定等于“新增一套代码”：

- 协议相同，仅账号、域名或认证参数不同：复用已有驱动；
- 请求、签名或返回结构不同：实现新的驱动。

建议统一驱动能力：

```text
能力声明
订单校验
报价（供应商支持时）
创建运单
获取面单
取消运单
查询轨迹
生成交接清单（供应商支持时）
```

供应商最终实重、最终收费重和实际成本的来源采用统一优先级：

```text
1. 供应商接口回传或查单接口返回（优先）
2. 供应商账单 Excel 导入并匹配订单（兜底）
```

不同供应商可在渠道配置中声明其实际数据来源和字段映射。不能从 FedEx 或其他供应商接口取得最终数据时，不影响面单创建；系统在账单导入后将匹配到的订单转入会计实际对账。客户余额的补扣或退款仍必须由会计确认，不能因接口回传或导入文件自动变动。

### 当前首批对接

- 首个联调供应商为 **FedEx 官方 REST API 测试环境**；
- 先实现 OAuth 授权、创建面单、取消面单与查询／追踪，并通过渠道实例配置测试账号；
- UPS、DHL、代理商及中转站在 FedEx 测试闭环验证后接入。

### 待确认

- 各供应商是否支持幂等请求；
- 中转站是否完全兼容官方协议；
- 是否需要供应商自动故障切换；
- 是否需要服务故障时切换到备用渠道；当前规则为每个服务固定对应一个渠道。

## 4. 安全边界

### 建议方案

- 供应商密钥仅保存在后端，不返回前端；
- 前端正常下单选择服务，不直接信任前端传入的供应商账号或渠道；
- 后端通过服务固定关联的渠道，取得对应的供应商账号与接口驱动；
- 管理员可以在受控权限下强制指定供应商；
- 客户接口不得返回供应商成本、账号密钥和平台利润；
- 保存供应商请求与响应时，对密码、Token 和个人敏感数据脱敏。
